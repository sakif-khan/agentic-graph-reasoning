\section{The AGR Framework}\label{sec:framework}

AGR inverts the usual agent pattern. It does not hand the model a set of
tools through native function-calling and let the model drive the loop.
Instead, a program orchestrates every step, calls the graph tools
deterministically, and consults the model only at bounded decision
points, through prompts constrained to return JSON. Three consequences
follow. Every graph operation is logged by construction rather than
reconstructed from the model's account of what it did. Budgets are
enforced by counters a router checks, not requested in a prompt the
model may ignore. And a malformed model response degrades one decision
rather than corrupting control flow: every call is wrapped in a parser
that, on failure, spends one metered retry asking the model to repair
its own output before falling back. The rest of this section specifies
the loop that produces a traversal (\Cref{sec:statemachine}), the layer
that checks a draft against it before an answer is emitted
(\Cref{sec:verification}), and the budgets that bound the whole loop's
cost (\Cref{sec:budgets}).

\subsection{State Machine and Tool API}\label{sec:statemachine}

\Cref{fig:statemachine} gives the topology: six agent nodes over a
shared typed state, with three cycles. The \textbf{Planner} decomposes
the question into an ordered chain of sub-objectives in one model call.
\textbf{Explorer} and \textbf{Evaluator} form a search loop. The
explorer expands the frontier, and the evaluator judges whether the
active sub-objective is satisfied. The \textbf{Backtracker} restores an
earlier, higher-scoring frontier and bans the edges that led away from
it. That ban list is what turns backtracking into a search operation.
Without it, a deterministic scorer facing the same restored frontier
would select the same edges again. Two properties of the topology matter
beyond the nodes themselves. It contains cycles rather than running once
through, because exploration continues until the evaluator is satisfied
and verification can send the agent back to explore. And every path from
Evaluator to Answerer passes through the \textbf{Verifier}. No route
reaches the Answerer without it. That routing is the structural
expression of this paper's contribution and the subject of
\Cref{sec:verification}.

Five graph operations back this loop. They are parameterised Cypher
templates, not free-form queries the model would write itself. A
generated-query failure is indistinguishable, in the results, from a
reasoning failure, and this paper's central claims are about reasoning
and verification, not about syntax. Only four of the five are reachable
from a node in the final design. \textsf{verify\_triple} was built
first, to check a claim $\langle h,r,t\rangle$ by asking whether that
exact relation held between the two entities. It did not survive contact
with generated text. Claim decomposition phrases relations in English
(``played for'', ``is the capital of''), and those phrases rarely
correspond to a single Freebase predicate, so matching on them rejected
claims that were true. \textsf{verify\_connection} replaced it. It drops
the relation and asks only whether the two entities are adjacent,
directly or through one mediator node. That is the check
\Cref{sec:verification} actually uses. \textsf{verify\_triple} remains
in the API and in its unit tests, but nothing in the running loop calls
it.

Each candidate edge the Explorer considers is scored by
\[
  \mathrm{score}(c) \;=\; \alpha \cos\!\big(v_{\mathrm{rel}(c)},\,
  v_{\mathrm{obj}}\big) \;+\; (1-\alpha)\, \mathrm{LLM}(c),
\]
which blends two signals at the frozen $\alpha = 0.7$. The first is the
cosine similarity between the candidate relation's embedding and the
embedding of the \emph{active sub-objective}. The objective, not the
original question, is what gets embedded, and that substitution is the
concrete mechanism through which decomposition is meant to help. The
second is a batched model judgement over a pre-filtered shortlist of
twenty candidates. The blend is applied after the model call rather
than inside the prompt. A prompt free of any configuration value lets
an $\alpha$ sweep reuse one set of cached responses across every
condition. Setting $\alpha = 1$ disables the model term entirely, which
is the ablation \Cref{sec:attribution} reports.

\subsection{Structural Verification Layer}\label{sec:verification}

The navigation loop above ends with a set of traversed triples and a set
of accumulated candidate entities. Nothing in it constrains what the
final answer \emph{asserts}. The verifier is the check that does. A
single model call drafts prose, extracts the entities the draft asserts
as its answer, and decomposes the draft into atomic claims $\langle h,
r, t \rangle$ over entity \emph{names}, since the model has never seen a
graph identifier. The relation slot is left as free text. Asking the
model to name a Freebase predicate would fail as unreliably as
\textsf{verify\_triple} did.

Each claim is routed through up to three tests, and it leaves at the
first one that settles it. \textbf{Traversed adjacency} collapses the
traversed triples into an undirected set of endpoint pairs. A claim is
supported if its pair is in that set, and every traversed triple joining
the pair is attached as citable evidence. This is the only route of the
three that attaches evidence. \textbf{\textsf{verify\_connection}}
catches claims whose endpoints were both reached but never walked
together. It queries the full graph for the same relation-agnostic
adjacency. Claims that clear neither route, together with those naming
an entity the agent never traversed at all, fall to an
\textbf{entailment check}: one batched model call judging each remaining
claim against the same fact window the drafter saw. The order is
deliberate. Symbols decide, and the model is consulted only where the
graph is silent. Cheap-to-expensive ordering also means the model
adjudicates a residue rather than every claim.

The router that follows has three outcomes. No unsupported claim routes
to \textsf{grounded}, and the draft is emitted verbatim with no further
model call. An unsupported claim with verification, depth, and time
budget remaining routes to \textsf{retry}: the verifier re-targets the
agent on the first unsupported claim, and control returns to the
Explorer. Otherwise the router takes \textsf{give\_up}. One rewrite call
then restates the draft around a \emph{deterministically filtered}
entity list. An entity survives if it appears in a supported claim or in
no unsupported claim. An earlier design let the model regenerate the
list itself, and that reintroduced exactly the ungroundedness the layer
exists to prevent.

The layer's reach should be stated plainly here, because it bears
directly on how the null result of \Cref{sec:attribution} should be
read. On the $80$-question development set used to validate this design,
$77$ questions asserted no unsupported claim and took the grounded path
at zero additional model cost. The remaining $3$ took \textsf{give\_up}.
The retry route did not fire once on that set, because every question
that reached the verifier with an unsupported claim had already
exhausted its depth budget by the time it got there. On most questions,
then, the layer is a pass-through that certifies a draft rather than a
mechanism that visibly intervenes. \Cref{sec:results,sec:attribution}
report what it measurably changes at test scale. Engineering detail
beyond that, including defects found along the way and recorded rather
than quietly repaired, is in the repository rather than reproduced here.

\subsection{Budgets and Termination}\label{sec:budgets}

\Cref{tab:budget} lists the caps that bound every run. Routers and the
model client enforce them; no prompt requests them. Three of them
(depth, wall-clock, and verification iterations) are checked at two
separate sites each, because the \textsf{retry} edge re-enters the
Explorer without passing back through the router that would otherwise
catch it. Closing that gap is what lets \Cref{tab:budget} be called a
guarantee rather than a convention. The two rows below the rule are not
budgets but tool-layer caps. They bound what the agent can see rather
than what it can spend, and \Cref{sec:baselines} shows why they matter
for the comparison.

Every cycle in \Cref{fig:statemachine} therefore passes through a router
that checks or decrements a monotone counter. So no sequence of model
outputs, however adversarial, can produce a non-terminating run. The
cost of enforcing this is small in the common case. The grounded path
above adds nothing beyond the single drafting call already required to
produce a draft. At test scale, removing the layer altogether saves
$2\%$ and $6\%$ of tokens on the two ablation half-splits
(\Cref{tab:ablation}). Whatever the case for or against the layer, it is
not a cost argument.
